# AGENTS.md — Lootly Agent Entry Point

Этот файл является обязательной точкой входа для любого ИИ-агента, который разрабатывает Lootly.

## 1. Область действия

Инструкции этого файла применяются ко всему репозиторию.

Если задача относится к Lootly и агент имеет доступ к репозиторию, он должен ДО планирования и изменения кода прочитать этот файл и выполнить описанную ниже загрузку контекста.

## 2. Обязательная загрузка контекста

В начале КАЖДОЙ задачи прочитай:

1. `.agents/lootly-agent.md`
2. `.agents/qa-agent.md`
3. `.agents/RULES.md`
4. `docs/BUSINESS_REQUIREMENTS.md`
5. `docs/TECHNICAL_REQUIREMENTS.md`
6. `docs/ARCHITECTURE.md`

Не полагайся на память о содержимом этих файлов: при работе с репозиторием актуальная версия в Git является источником истины.

## 3. Роли агентов

### Development Agent
`.agents/lootly-agent.md` отвечает за анализ задачи, проектирование и реализацию.

### QA Agent
`.agents/qa-agent.md` выполняет независимую проверку результата после реализации. QA Agent не должен автоматически считать решение корректным только потому, что его создал Development Agent.

QA Agent обязан:
- проверить diff против требований и архитектуры;
- проверить тесты, миграции, безопасность, идемпотентность и edge cases;
- запустить доступные quality gates;
- классифицировать проблемы по severity;
- блокировать завершение задачи при критических/высоких проблемах или падающих обязательных проверках.

## 4. Маршрутизация skills

После чтения базового контекста классифицируй задачу и подключи все подходящие skills.

| Тип задачи | Обязательный skill |
|---|---|
| Источник объявлений, adapter, polling, scheduler, дедупликация, фильтры, обработка listing | `.agents/skills/marketplace-monitoring/SKILL.md` |
| Рыночная цена, медиана, Deal Score, Risk Score, comparable listings, price analytics | `.agents/skills/deal-scoring/SKILL.md` |
| Любое изменение кода перед завершением задачи | `.agents/skills/testing-and-review/SKILL.md` |

Если задача затрагивает несколько областей, используй несколько skills.

## 5. Обязательный рабочий цикл

Для каждой инженерной задачи следуй циклу:

```text
User request
   ↓
Read AGENTS.md
   ↓
Load base project context
   ↓
Classify task and load skills
   ↓
Development Agent: inspect → design → implement → tests
   ↓
QA Agent: independent review + quality gates
   ↓
QA passed? ── yes ──> report/PR and continue
   │
   no
   ↓
Development Agent fixes defect
   ↓
QA Agent re-checks
```

## 6. Политика непрерывной работы и 3 итераций

Если пользователь явно поручил продолжать разработку, агент НЕ должен останавливаться между успешно завершенными внутренними этапами только ради подтверждения.

Прерывание допустимо только если:

1. требуется продуктовый, юридический, инфраструктурный или иной выбор пользователя, который нельзя надежно вывести из требований;
2. требуется секрет/credential/внешний доступ, который агент не может получить сам;
3. возник блокер разработки или тестирования, который не удалось устранить за 3 полных итерации.

Одна итерация блокера состоит из:
`диагностика → изменение/исправление → повторная проверка`.

Для одного и того же блокера:
- выполнить до 3 самостоятельных итераций;
- использовать новые диагностические данные на каждой следующей итерации;
- не повторять идентичное исправление без новых оснований;
- после успеха продолжить разработку без запроса подтверждения;
- после третьей неуспешной итерации остановиться и сообщить пользователю: симптом, выполненные попытки, доказательства/логи, текущую гипотезу и какое решение/доступ нужен.

## 7. Правила выполнения задач

Агент должен:

- выполнять задачу самостоятельно, если требований достаточно;
- не просить повторно информацию, которая уже есть в репозитории или диалоге;
- предпочитать минимальное завершенное изменение крупной переписке;
- соблюдать текущую архитектуру;
- обновлять документацию при изменении контракта или требований;
- не выдавать предположение о внешнем API за проверенный факт;
- не обходить CAPTCHA, антибот-защиту или иные технические ограничения площадок;
- не добавлять секреты в Git;
- не отправлять изменения в `main` напрямую, если пользователь явно не попросил об этом;
- по умолчанию работать в отдельной ветке и оформлять проверяемый PR для существенных изменений.

## 8. Definition of Done для любой задачи с кодом

Задача не считается завершенной, пока QA Agent не подтвердил:

- изменение соответствует бизнес-требованиям;
- изменение соответствует архитектуре;
- соблюдены `.agents/RULES.md`;
- критическая логика покрыта тестами;
- нет обнаруженного риска повторной обработки/уведомления;
- внешние ошибки обрабатываются;
- секреты не появились;
- миграции проверены;
- документация обновлена при необходимости;
- обязательные доступные quality gates проходят.

Для проверки обязательно использовать:
`.agents/skills/testing-and-review/SKILL.md`.

## 9. Поведение ChatGPT / Codex при работе с Lootly

Если пользователь просит ChatGPT/Codex изменить Lootly через GitHub:

1. получить актуальный `AGENTS.md`;
2. загрузить указанные им инструкции;
3. выполнить работу Development Agent;
4. выполнить независимый проход QA Agent;
5. при дефектах самостоятельно выполнить до 3 циклов исправления;
6. для существенных изменений использовать feature branch + Pull Request;
7. сообщить пользователю результат, проверки и PR.

## 10. Приоритет инструкций внутри проекта

При конфликте проектных инструкций используй следующий порядок:

1. безопасность и ограничения платформы;
2. `.agents/RULES.md`;
3. бизнес-требования;
4. технические требования;
5. архитектура;
6. task-specific skill;
7. локальные соглашения реализации.

Если требование пользователя сознательно меняет продуктовые или технические требования, изменение требований должно быть отражено в соответствующей документации вместе с кодом.
